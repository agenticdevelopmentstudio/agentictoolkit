# Extension Host

## Overview

This component is three cooperating roles that together run a VS Code web extension's JavaScript and keep the running set of extensions in step with what the extension registry holds. The host owns one extension's JavaScript execution context inside a single process-wide JavaScript virtual machine shared across every extension's context: it resolves and reads the extension's declared `browser` entry point, compiles it as a CommonJS module wrapper, evaluates it, and calls its exported `activate(context)`, tracking a single activation-state value (not yet activated, activating, activated, terminal — cancelled or failed, disposed) whose evaluation order is explicitly documented as load-bearing — a "ladder of guards" anti-pattern that produced "four rounds of the same defect" before this single state value replaced it. The installer owns one host plus eight per-extension vscode namespace adaptors (for commands, languages, workspace, language models, window, webviews, tree views, and diagnostics) inside one installation, and the installer itself reconciles the whole running set against the registry's extensions by an identity that includes the entry point's on-disk size and modification date, not merely the extension's identifier — so an author's code edit is caught even when the manifest is byte-identical. The ledger is a small, injectable component, shareable across hosts, that deduplicates every VS Code API member an extension reached for and this host does not implement, keyed by extension identifier and member path, distinguishing a hard use from a feature-detection probe.

All three roles are confined to a single execution context; the host, and every JavaScript value or execution context it touches, is explicitly documented as unsafe to share across execution contexts, and the doc comments state the confinement is deliberate — every adaptor these types call into is itself confined to that same single context, and a host that hopped contexts would have to marshal JavaScript values across them. The one documented exception is compiling the module, which parses (but never executes) the extension's module off that single context on a separate task, carrying the JavaScript execution context across that one hop through a private thread-crossing box explicitly asserted to be safe to share, justified by the shared JavaScript virtual machine's own internal lock making cross-thread use of the underlying JavaScript engine thread-safe by construction.

## Behavioral Requirements

- **activation-state-precedence**: The host's activation state MUST evaluate in the fixed order disposed, activated, terminal, activating, not-yet-activated — never in field-declaration order — so that a cancellation landing after a successful activation is still reported as activated, and a failure recorded while activation is being performed outranks the activating state a racing caller might still observe.
- **activate-idempotent-shared-outcome**: Activating the host MUST be a no-op that returns immediately when the activation state is already activated, and two concurrent callers MUST share the single in-flight activation task rather than each evaluating the module.
- **activate-refuses-when-disposed-or-terminal**: Activating MUST throw a host-disposed error on a disposed host, and MUST throw the mapped cancelled/already-failed error on a terminal host, without re-evaluating the module.
- **activate-no-timeout**: Activating MUST NOT impose an internal timeout on an extension's own `activate()` promise; the only two ways to end a suspended activation are cancelling the calling task (which reports as cancelled) and disposing the host.
- **activate-cancellation-shared**: A cancellation from any one caller of activate MUST end the shared activation for every other awaiting caller.
- **module-evaluated-terminal-boundary**: The module-evaluated flag MUST be set exactly once, immediately before the module's run call, and every route into the terminal state MUST test this flag rather than infer it from which step of evaluation it is inside.
- **failure-before-boundary-is-retryable**: A failure that occurs before the module-evaluated flag is set (entry-point resolution, disk read, compile) MUST leave the host not-yet-activated and eligible for a later activate call.
- **failure-after-boundary-is-terminal**: Any failure at or after the module's run call (a synchronous throw, a rejected `activate()` promise, a throwing `.then` getter, a top-level throw, or a cancellation landing once the module is running) MUST record a termination reason and MUST refuse every later activate or define-vscode-member call on that host.
- **terminal-reason-keeps-first**: Recording a termination reason MUST keep the first reason recorded and MUST be a no-op on every subsequent call, so a cancellation and a failure racing to the same boundary cannot overwrite each other's diagnostic.
- **dispose-idempotent**: Disposing the host MUST be safe to call more than once and safe to call on a host that never activated.
- **dispose-releases-suspended-activation**: Disposing MUST resume any suspended activation with a host-disposed error, since an extension's own `activate()` promise may never settle and there is no timeout to fall back on.
- **dispose-cancels-every-timer**: Disposing MUST cancel every outstanding timer task and clear the tracking table, so no `setTimeout`/`setInterval` task can reach JavaScript again after teardown.
- **dispose-releases-context**: Disposing MUST replace the execution context's exception handler with one that safely records the exception, rather than clearing it, since the underlying engine calls whatever handler is set unconditionally, and MUST release the activation context, the runtime, and the execution context itself.
- **dispose-subscriptions-before-context**: Disposing MUST dispose the activation context's subscriptions before releasing the execution context, so the extension's own disposables are still callable at the moment they run.
- **dispose-subscriptions-idempotent**: Disposing the activation context's subscriptions MUST run at most once per host, so a caller (such as an installation's own dispose operation) that calls it ahead of the host's own dispose produces exactly one pass over `context.subscriptions`.
- **dispose-subscriptions-releases-values-promptly**: Disposing the activation context's subscriptions MUST release each JavaScript value it produces promptly rather than deferring their release to the end of the whole pass, because every JavaScript value produced along the way holds its own execution context strongly and would otherwise keep the context alive past the promise disposing makes to release it.
- **finalization-safety-net-cancels-timers**: The host's own finalization MUST cancel every timer task as a safety net for a host dropped without an explicit dispose call, but MUST NOT be relied upon as the primary teardown path, since a host with an in-flight activation task (which strongly captures the host) never reaches finalization at all.
- **define-vscode-member-refuses-terminal-or-disposed**: Defining a vscode member MUST throw a host-disposed error on a disposed host and the mapped terminal error on a terminal host, never silently queuing a definition nothing will replay and never installing a live implementation into an abandoned runtime.
- **define-vscode-member-replays-on-runtime**: A definition made before a runtime exists MUST be queued and applied immediately once the runtime is installed; a definition made after activation MUST be applied immediately.
- **define-vscode-member-withdraws-on-refusal**: A definition the shim refuses (an unknown namespace) MUST be removed from the queue rather than left there, so the host remains activatable and the same bad definition does not fail every future activate call.
- **deferred-value-resolved-at-apply-time**: A deferred value's implementation MUST be resolved against a live JavaScript execution context only at the moment it is applied, never at the moment the member is defined, since every caller defining a member runs before any context exists.
- **live-value-re-read-per-access**: A live value's implementation MUST be re-read on every JavaScript access rather than resolved once and cached, so members reporting app state (`vscode.workspace.workspaceFolders`, `vscode.workspace.name`) never freeze to whatever was true at install time.
- **timer-delay-clamped-nan-safe**: Computing a timer's clamped delay MUST compute the equivalent of `min(max(0, milliseconds), maximum delay) / 1000`, with `0` as the first argument to the max comparison (not the second), so that a `NaN` delay collapses to `0` rather than propagating into a duration value that traps on an unrepresentable input.
- **timer-cancel-validates-before-truncating**: Cancelling a timer MUST validate that the raw numeric id is finite, integral, and within the 32-bit signed integer range before truncating it, and MUST do nothing (never round onto an unrelated timer) when validation fails.
- **timer-task-count-asserts-not-clamps**: Recording that a timer task finished MUST assert and log a fault rather than clamp to zero when the running-timer count is not already positive, since a double-decrement indicates a timer task finished twice, a bug this counter exists to surface rather than hide.
- **console-message-always-logged**: Every `console.*` call MUST produce a log line at the mapped level, and MUST additionally invoke the console-message observer when one is set, even when no observer is attached.
- **not-implemented-recorded-once-per-member**: A member reached for that this host does not implement MUST be recorded in the ledger, with only the first access producing a log line, so a member reached for in a loop does not flood the log.
- **negative-probe-recorded-separately**: A feature-detection probe (`'x' in vscode.commands`, `Object.keys(...)`) that finds nothing MUST be recorded, sharing the same ledger row as a hard use of the same member but incrementing its probe count rather than its use count.
- **entry-point-requires-browser-not-main**: Resolving the entry point MUST throw a requires-Node-runtime error when the manifest declares `main` but not `browser`, and MUST throw a no-entry-point error when it declares neither, never treating a Node-only extension as a generic load failure.
- **entry-point-must-not-escape-directory**: Resolving the entry point MUST resolve the declared `browser` path through the shared resource-path resolver and MUST throw an entry-point-escapes-directory error when the resolved path falls outside the extension's own directory, including a sibling directory sharing a name prefix.
- **compile-runs-nothing**: Compiling the module MUST produce a callable closure without executing any of the extension's top-level statements, which is the property that allows the compile step alone to run off the host's own execution context.
- **entry-point-attributed-in-stack-traces**: Compiling the module MUST attribute the wrapped source to the entry point's own location, so a syntax error or a thrown exception names the extension author's own file and line.
- **exports-required-non-empty**: Evaluating the module MUST throw an entry-point-threw error when the module's run call yields `undefined`/`null` exports, distinct from a thrown exception.
- **activate-absence-is-not-an-error**: Calling activate MUST log (not throw) when the module's exports have no `activate` function, since a manifest-only extension that contributes solely through side effects is legal.
- **activate-rejection-getter-throw-reported**: Calling activate MUST report a thenable whose `.then` property getter throws as an activation failure, rather than hanging indefinitely because the shim's completion callback is never invoked in that case.
- **finish-activation-resumes-exactly-once**: Finishing activation MUST resume the stored, suspended activation at most once and MUST be a safe no-op when nothing is pending, since up to four routes (the shim's completion block, the thenable-getter-throw path, disposing the host, and a cancelling caller) can race to end the same activation.
- **describe-reentrancy-bounded**: Describing an exception MUST return a fixed literal string rather than recursing when called while already describing another exception, so a hostile self-referential `Proxy` that throws while being described cannot overflow the native stack.
- **vscode-uri-and-vocabulary-installed-eagerly**: Installing the runtime MUST install the command-dispatch trampoline, `vscode.Uri`, the language-model message vocabulary, the text-geometry classes, and the diagnostic value types on every activation, before any adaptor-registered member and before the extension's own module code runs, and MUST NOT route any of these five through the define-vscode-member queuing path, since they are host ceremony reinstalled identically every time rather than adaptor state to be replayed.
- **install-vscode-members-sorted**: Installing vscode members MUST iterate the member table's keys in sorted order, never in raw, unordered iteration order, so the install order (and therefore any log line describing a failed install) is stable across runs.
- **host-globals-removed-after-shim-setup**: Installing the runtime MUST remove the runtime-setup globals (`globalThis.__extensionRuntime`, `globalThis.__host`) after wiring the runtime, so extension code has no direct line to the host's timer/console/ledger bridge once setup is complete.
- **installation-adaptor-teardown-order**: Disposing an installation MUST run, in this exact order: dispose the host's activation-context subscriptions; unregister every remaining entry in the activation-stub command table; dispose all eight adaptors (commands, languages, workspace, language models, window, webviews, tree views, diagnostics); then dispose the host itself last — because the adaptor withdrawals call back into JavaScript (a panel's `onDidDispose`, a tree view's teardown) and require a live runtime.
- **installation-dispose-idempotent**: Disposing an installation MUST be a no-op on a second call.
- **activation-command-double-press-forwards-both**: Dispatching a command after activation MUST retire its stub token only if present, without requiring it, before forwarding, so that a second command press queued while activation is still in flight is forwarded on its own merits rather than dropped because the token was already taken by the first press.
- **activation-stub-leaves-owned-commands-alone**: Registering activation-stub commands MUST NOT register a stub over a command id already present in the command registry, and MUST log that the extension's `onCommand:` trigger for that id will never fire.
- **installer-reconcile-identity-not-identifier**: Reconciling the running set MUST key "already installed" on the manifest plus directory plus the entry point's own file signature (size and modification date), never on the bare extension identifier, so an author's on-disk code edit is detected and the host is rebuilt even when the manifest is unchanged.
- **installer-reconcile-dispose-before-rebuild**: Reconciling MUST dispose an outgoing installation before constructing its replacement for the same identifier, never leaving both live at once, since both would otherwise record against the same extension identifier in five adaptors simultaneously.
- **installer-reconcile-disables-removed-extensions**: Reconciling MUST dispose and remove every installation whose identifier is no longer in the enabled set.
- **installer-bring-up-replays-completed-scan-only-if-current**: Bringing up a newly installed extension MUST replay the workspace-scanned activation trigger against it only when the completed scan's roots still equal the live workspace roots, never a stale scan from a since-closed project.
- **installer-bring-up-replays-open-documents-live**: Bringing up a newly installed extension MUST replay document-opened triggers by reading the open-document languages live at call time, never from a remembered set, so a document since closed cannot activate an extension.
- **workspace-scan-reused-per-workspace**: Starting a workspace scan if needed MUST reuse the completed scan when its roots already equal the live workspace roots, and MUST NOT start a second scan while one with the same roots is already in progress.
- **workspace-scan-race-safe-on-root-return**: The workspace scan's completion handler MUST re-read the live workspace roots and discard a scan's result (retrying rather than recording it) when the live roots no longer match the roots the scan was started against — covering an A-to-B-and-back-to-A root change during an in-flight scan of B.
- **workspace-scan-depth-and-entry-capped**: Scanning the workspace roots MUST stop descending into a directory once the walk's depth reaches the depth limit (6) and MUST stop collecting once the number of found entries reaches the entry limit (20,000).
- **workspace-scan-skips-generated-directories**: Scanning the workspace roots MUST skip descending into any directory named in the skipped-directory-names set (`.build`, `.git`, `.svn`, `.venv`, `DerivedData`, `Pods`, `__pycache__`, `build`, `dist`, `node_modules`, `target`, `vendor`).
- **workspace-scan-includes-dotfiles**: Scanning the workspace roots MUST NOT skip hidden files while walking, so dotfile-based `workspaceContains:` patterns (`.vscode/launch.json`, `.eslintrc*`) remain matchable.
- **workspace-scan-incomplete-signal**: NEEDS REVIEW: Not implemented in source. Scanning the workspace roots resolves each directory entry's directory-or-file status, defaulting to "not a directory" on any failure and continuing the walk with no signal that the walk is now incomplete. The completed-scan result carries no incompleteness flag comparable to the extension registry's own nil-on-incomplete-scan contract, so a `workspaceContains:` extension can be told a pattern does not match a workspace the scan never actually finished reading, with nothing anywhere recording that the answer might be wrong.
- **webview-panel-claim-order-deterministic**: Restoring a webview panel MUST resolve a webview view-type contested by more than one installed extension by sorting claimants by identifier and choosing the first, and MUST log when more than one claimant exists.
- **contributed-view-resolved-by-manifest-ownership**: Resolving a contributed webview view or tree view MUST resolve strictly to the single extension named as its owner in the manifest, never by a claims-based contest, since a contributed view's ownership was already declared in the manifest.
- **contributed-view-will-appear-is-a-broadcast**: A contributed view about to appear MUST notify every installed extension's activation-trigger check for that view being shown, unlike the owner-only resolution operations, because `onView:` may be declared by any extension against any view id, including one it does not own.
- **not-implemented-ledger-dedup-by-key**: The ledger MUST deduplicate by extension identifier and member path together, keeping the first access timestamp and incrementing its use count (for a hard use) or its probe count (for a feature-detection probe) on every subsequent call for the same key.
- **not-implemented-ledger-accessors-sorted**: The ledger's two read operations (all accesses, and accesses for one extension) MUST both return rows ordered by extension identifier then member path, never in insertion order.

## Appearance

Not applicable — this is a JavaScript execution runtime, its per-extension installation/adaptor wiring, and an access ledger, not a visual component.

## Edge Cases

- **Null/empty input**: An extension manifest with neither `main` nor `browser` is not an error at all — a no-entry-point error is thrown only if activate is called; a manifest-only extension that contributes solely through its manifest and never calls activate is legal and unremarkable.
- **Boundary values**: Computing a timer's clamped delay is exercised across `0`, the largest representable floating-point value, positive infinity, `NaN`, a negative value, the documented 32-bit `setTimeout` ceiling itself, and one millisecond past it — every one of those inputs must produce a representable duration rather than a trap.
- **Boundary values — timer id truncation**: Cancelling a timer receives the raw floating-point id an extension wrote to `clearTimeout`/`clearInterval` rather than a 32-bit integer, specifically so that an id like `4294967297` (one past the 32-bit signed maximum) is rejected outright instead of being silently truncated by the underlying engine's own 32-bit coercion onto an unrelated live timer with id `1`.
- **Concurrent access — shared activation**: Two or more callers invoking activate concurrently on the same host share one task and one outcome; a cancellation from any one of them ends the activation for all of them, per **activate-cancellation-shared**.
- **Concurrent access — activation racing teardown**: Calling activate reads the activation state (rather than an ad-hoc disposed check) immediately before installing its continuation, because a host observer invoked from inside the extension's own top-level code can dispose the host mid-evaluation, and the continuation must not be installed on a host already told to stop.
- **Concurrent access — workspace scan racing a moving workspace**: Starting a workspace scan if needed re-reads the live workspace roots rather than trusting the roots it started with, specifically to cover an A-then-B-then-back-to-A root change while a scan of B is still running; recording B's result under a workspace now showing A would both misfire `workspaceContains:` activations and leave the completed-scan result permanently wrong about which project is open.
- **Concurrent access — double command press during activation**: Dispatching a command after activation retires the activation-stub token only if present, without requiring it, because a user pressing an activation-triggering command twice before the extension finishes activating queues two dispatches, and an admission check that required the token would silently drop the second press.
- **Error states — hostile JavaScript**: An extension that replaces `Function.prototype.call`/`.apply`, or throws a self-referential `Proxy` from its own top-level code (`aPoisonedFunctionPrototypeApplyCannotSilenceTimerCallbacks`, `aThrownValueThatThrowsWhileBeingDescribedIsNotFatal`), must not be able to fake a successful activation, silence a timer callback, or crash the host process via unbounded native recursion during exception description.
- **Error states — a rejection with no `Error` shape**: Calling activate reports a rejected `activate()` promise whose rejection reason is not an `Error` instance (`aRejectionThatIsNotAnErrorIsStillReported`) as an activation-threw failure rather than crashing or silently succeeding.
- **Error states — a `.then` getter that throws**: A thenable whose `.then` property getter itself throws leaves calling activate to go through the pending-exception path rather than through the shim's completion callback, and is reported as a failure rather than left to hang the activation forever (verified against the real underlying JavaScript engine, per the source's own comment).
- **Error states — adaptor spells a namespace wrong**: Defining a vscode member with a namespace the shim's table does not have is the *adaptor's* bug, not the extension's; the apply-or-withdraw operation withdraws the bad definition and logs it with the calling adaptor's own file and line, so the member stays a not-implemented stub on every later activation rather than failing every future activate call identically.
- **Offline/disconnected**: Not applicable in the networking sense — this component performs no networking of its own; the closest analogue is a workspace that closes mid-scan, covered above under concurrent access.
- **Error states — incomplete workspace scan**: see the open question on workspace-scan-incomplete-signal above.

## Privacy

- **Data collected**: The host reads the extension's own bundled JavaScript entry point off disk and runs it; the ledger records extension-authored identifiers and API member-path strings an extension reached for. None of the three roles reads or transmits a credential, token, or other secret value of its own.
- **Extension-authored content is privacy-annotated, not filtered**: Every logged interpolation of extension-controlled text — `console.*` output, an extension identifier, a thrown exception's message and stack, a define-vscode-member origin, a member path recorded in the ledger — is deliberately marked public in the host's and installer's own logging calls, rather than redacted. This is a deliberate choice to keep extension diagnostics readable in the system log, not an oversight; it means an extension author's own file contents, console output, and error text are treated as debuggable diagnostic data, not as a secret the host must protect.
- **Storage**: The ledger's entries and the host's own runtime state are in-memory only for the life of the process; nothing in these three roles persists an entry to disk.
- **Transmission**: Not applicable — none of the three roles performs networking.
- **Retention**: A ledger entry lives for the life of the ledger instance (typically the app process); the host's and an installation's state is released on dispose.

## Platform Notes

- **AppKit / UIKit**: This is the source. `ExtensionHost.swift`, `ExtensionHostInstaller.swift`, and `NotImplementedLedger.swift` (all in `packages/apple/AgenticToolkit/macOS/Features/Extensions/Host/`) are the host, the installer (plus `ExtensionHostInstallation`), and the ledger, respectively. `ExtensionHost.swift` is part of `AgenticToolkitCore`-adjacent macOS-only code importing `JavaScriptCore` and `OSLog`; `ExtensionHostInstaller.swift` additionally imports `AppKit` for `NSWindow`/`NSAlertMessagePresenter` (the `frontWindow` seam) and `AgenticDeveloperToolkitUI` for the pane/presenter types the eight adaptors are built over. All three types are declared `@MainActor`; `ExtensionHost`, and the `JSValue`/`JSContext` values it produces, are explicitly documented as not `Sendable`. The single-execution-context confinement referenced throughout the normative text above is exactly this `@MainActor` declaration; "JavaScript execution context" and "JavaScript value" are `JavaScriptCore.JSContext` and `JavaScriptCore.JSValue`; the shared JavaScript virtual machine is `JSVirtualMachine`. The one off-context hop, in `compileModule(source:entryPoint:)`, runs inside a `Task.detached`, carrying the context across that hop through a private `JSCrossThread<Value>: @unchecked Sendable` box. The five activation-state values are `ExtensionHost.activationState`'s cases `.neverActivated`, `.activating`, `.activated`, `.terminal(.cancelled | .failed)`, `.disposed`; the recorded termination reason is `TerminationReason`, kept by `markTerminal(_:)`; the module-evaluated flag is the stored property `moduleEvaluated`; the shared in-flight activation task and its suspended continuation are `activationTask` and `activationContinuation`, ended via `finishActivation(_:)`; disposing the activation context's subscriptions is `disposeSubscriptions()`, guarded by `subscriptionsDisposed` and wrapping its JavaScriptCore calls in `autoreleasepool` (this is what "releases each JavaScript value promptly" means above); the host's finalization is its `isolated deinit`. Defining a vscode member is `defineVSCodeMember(namespacePath:name:implementation:fileID:line:)`, queuing into `vscodeMemberDefinitions` and applying or withdrawing via `applyOrWithdraw`; a deferred value is `DeferredVSCodeValue`, resolved inside `apply(_:to:)`; a live value is `LiveVSCodeValue`, re-read from `JSContext.current()`. Computing a timer's clamped delay is `ExtensionHost.clampedTimerDelaySeconds(milliseconds:)`, producing a `Duration.seconds`-representable result; cancelling a timer is `cancelTimer(rawTimerID:)`, truncating a raw `Double` to `Int32`; the running-timer count is `runningTimerTasks`, decremented by `timerTaskDidFinish()`; the mapped console level is `ExtensionConsoleMessage.Level`; the console-message observer is `onConsoleMessage`. Resolving the entry point is `resolveEntryPoint()`; compiling the module is `compileModule(source:entryPoint:)`; evaluating the module is `evaluateModule`; calling activate is `callActivate`; describing an exception is `describe(_:)`, guarded against recursion by `describingException`; installing the runtime is `installRuntime(runtimeSource:into:)`; installing vscode members is `installVSCodeMembers(_:onto:)`. The eight per-extension vscode namespace adaptors are `MainThreadCommands`, `MainThreadLanguages`, `MainThreadWorkspace`, `MainThreadLanguageModels`, `MainThreadWindow`, `MainThreadWebviews`, `MainThreadTreeViews`, and `MainThreadDiagnostics`; the activation-stub command table is `stubCommands`; the command registry is `commandRegistry`. Reconciling is `ExtensionHostInstaller.reconcile()`; the identity it keys on is `InstalledIdentity` (manifest plus directory plus entry-point `FileSignature`, the on-disk size and modification date); bringing up a newly installed extension is `bringUp(_:identity:)`; the open-document-languages seam is `seams.openDocumentLanguageIDs()`. Scanning the workspace roots is `ExtensionHostInstaller.scan(roots:)`, using a `FileManager` enumerator whose `.skipsHiddenFiles` is left unset and whose `enumerator.level` is compared against `scanDepthLimit`; the skipped-directory-names set is `skippedDirectoryNames`; a contributed view's declared owner is `ContributedView.extensionIdentifier`. The ledger is `NotImplementedLedger`, recording via `record(memberPath:extensionIdentifier:)`/`recordProbe`/`handleNegativeProbe`, and reading via `accesses`/`accesses(for:)` in `reportOrder`. Logging throughout both files goes through the shared `Loggable` protocol (subsystem `Bundle.main.bundleIdentifier`, falling back to `"nil"`); the file-system-service configuration entry is `ExtensionHostSeams.fileSystemService: FileSystemServicing`, defaulted to `FileSystemService()`; the ledger clock entry is `NotImplementedLedger.now: @MainActor () -> Date`. There is no UIKit port target in this repository today.
- **SwiftUI**: Neither file has a SwiftUI dependency. A SwiftUI host wanting to observe the host's console-message observer or the installer's installations would wrap them in an `@Observable` adapter, since neither type publishes `@Published`/`@Observable` state directly.
- **Compose**: A Kotlin port has no `JavaScriptCore` equivalent; the nearest analogue is embedding a JS engine such as J2V8 or a WebView-hosted `Duktape`/`QuickJS` binding, with the same one-VM-per-process, one-context-per-extension shape. `@MainActor` confinement maps to a single-threaded `CoroutineDispatcher` (e.g. `Dispatchers.Main`) every call is confined to; the off-main compile step maps to `withContext(Dispatchers.Default)` for the parse, resuming on `Dispatchers.Main` to run the module. `Task`-based timers map to `Handler(Looper.getMainLooper())` or a coroutine `delay`-loop that is explicitly cancellable, mirroring dispose-cancels-every-timer.
- **React/Web**: A TypeScript/Node host has no analogue for running a *second* JavaScript VM inside JavaScript at all; the closest real-world precedent is VS Code's own extension host process, which this component is deliberately modeled after in miniature (one process boundary per extension there, one JavaScript execution context per extension here). A web-hosted port would instead run each extension inside its own Web Worker or iframe sandbox, with `postMessage` standing in for the `__host` block-table bridge, and would need its own explicit timer-cancellation-on-teardown discipline since a Worker does not enforce it for you.
- **WinUI 3**: A .NET port would host each extension's JavaScript in a `ChakraCore`/`ClearScript` (V8 or JScript) engine instance, mirroring the one-VM-shared, one-context-per-extension shape given here. `@MainActor` confinement maps to requiring every call to originate on the UI thread (`DispatcherQueue.HasThreadAccess`), with the compile-only off-thread step mapped to `Task.Run` for the parse, resuming on the `DispatcherQueue` to run the module — the same split `compile-runs-nothing` documents. `Task`-based timers map to `DispatcherQueueTimer` or a cancellable `Task.Delay` loop; the NaN-safety concern in computing a timer's clamped delay has a direct analogue, since `TimeSpan.FromMilliseconds(double.NaN)` throws rather than trapping the process, so the same `Math.Max`/`Math.Min` clamp order is required before constructing the `TimeSpan`.

## Design Decisions

**Decision**: `activationState` is a single computed property with a fixed, documented precedence order (disposed, activated, terminal, activating, neverActivated) rather than a stored enum or a set of independent boolean flags each guard re-derives.
**Rationale**: The source's own comment states four prior rounds of fixes were each a correct answer to the route just demonstrated, and each left the resulting state reachable by another route because the state had no name — only a scatter of booleans each guard re-derived for itself. Naming the precedence once and reading it everywhere ends that cycle; `.terminal` outranking `.activating` specifically matters because `markTerminal(.failed)` runs inside `performActivation`'s `catch` several main-actor jobs before `activate()`'s own `defer` clears `activationTask`, and a second caller arriving in that window must see the same terminal answer as every later caller.
**Approved**: pending

**Decision**: `activate()` has no internal timeout, and the only two ways to end a suspended activation are cancelling the calling task or calling `dispose()`.
**Rationale**: A real extension may legitimately await a network round trip during activation, and a host that gave up at some fixed *n* seconds would report a failure that did not happen. Cancellation is the idiomatic Swift escape a caller already reaches for when it wants a timeout of its own, and `dispose()` is the unconditional teardown escape for every other case.
**Approved**: pending

**Decision**: `moduleEvaluated` — set exactly once, on the line immediately before the shim's `run` call — is the single field that decides whether a failure spends the host permanently or leaves it retryable, rather than inferring that boundary from which `do`/`catch` block a failure surfaced in.
**Rationale**: `compileModule` and `evaluateModule` both throw with zero extension statements executed in some paths (a syntax error, a missing shim) and with the module fully run in others; testing a single boundary field rather than the shape of the `catch` block is what lets `endActivation`'s cancellation path and `performActivation`'s failure path agree on exactly the same rule without duplicating it. The source states a prior version inferred terminality from the `do` block and incorrectly told a host whose extension file "merely would not parse" that its code had already run.
**Approved**: pending

**Decision**: Teardown is three separable phases in a fixed order — the extension's own `context.subscriptions`, then the eight adaptors, then `ExtensionHost.dispose()` — rather than one combined sweep.
**Rationale**: Every subscription entry reaches back through an adaptor (a registered command, an open panel, an owned collection), so subscriptions must be disposed while the adaptors are still standing; the adaptors' own withdrawal sweeps in turn call back into JavaScript (a panel's `onDidDispose`), so they must run before the runtime is released. The source notes an earlier version ran subscriptions last, inside `host.dispose()`, and a `dispose` block that called an already-withdrawn command silently dropped the work because `executeCommand` answers a rejected promise a `dispose` block never awaits.
**Approved**: pending

**Decision**: `clampedTimerDelaySeconds(milliseconds:)` computes `min(max(0, milliseconds), maximumTimerDelayMilliseconds)`, with the clamp floor as the *first* argument to `max`.
**Rationale**: `Duration.seconds(Double)` traps on any value it cannot represent, and the inputs reaching this function are the whole of `Double` including `NaN` and both infinities from one arbitrary `setTimeout` call. Swift's `max(x, y)` returns `x` for any comparison against `NaN` (every comparison against `NaN` is `false`), so `max(0, .nan)` is `0` while `max(.nan, 0)` is `NaN` — the argument order, not the choice of `max` before `min`, is what prevents a single extension's malformed `setTimeout` argument from crashing the whole process. The source notes this was confirmed by a mutation-testing survivor, not merely reasoned from first principles.
**Approved**: pending

**Decision**: `ExtensionHostInstaller.reconcile()` keys "already installed" on `InstalledIdentity` — the manifest plus directory plus the entry point's `FileSignature` (size and modification date) — rather than on the extension's bare identifier.
**Rationale**: `ExtensionRegistry.loadAll()` re-reads every manifest from disk on every rescan, so an extension whose author edited only its *code* (leaving the manifest byte-identical) previously produced a `LoadedExtension` the installer could not distinguish from the one already running, leaving the old code executing while the registry, contribution points, and settings UI all showed the new manifest. A `nil`-equals-`nil` signature (an entry point that cannot be resolved or stat'd) deliberately keeps the currently running host rather than tearing it down for a rebuild that would fail identically.
**Approved**: pending

**Decision**: `startWorkspaceScanIfNeeded()`'s completion handler re-reads the live workspace roots and compares them against the roots the scan was started with, rather than trusting `scanningRoots` alone.
**Rationale**: `scanningRoots` alone cannot distinguish a scan superseded by a *newer* scan (safe to discard) from the workspace moving from A to B and back to A while B's scan is still running — recording B's result at that point would file it as the answer for a workspace now showing A, replay it at every extension, and leave `completedScan` permanently wrong until another `workspaceDidChange()` happens to correct it. Comparing live roots and re-entering the scan when they disagree closes that hole at the cost of one extra idempotent call.
**Approved**: pending

**Decision**: `dispatchAfterActivation(commandID:arguments:)` retires the activation-stub token with `if let token = stubCommands.removeValue(forKey:)` rather than `guard let token = ... else { return }`.
**Rationale**: Activation is asynchronous, so a user pressing the same activation-triggering command twice before the extension finishes activating queues two dispatches, each carrying its own arguments. A `guard`-based admission ticket let only the first dispatch pass and silently dropped the second on the floor; forwarding on its own merits regardless of whether the token is still present ensures every invocation is honored.
**Approved**: pending

`separation-of-concerns` passes because `ExtensionHost` delegates entry-point path resolution to `ExtensionResourcePath`, activation-trigger matching to `ActivationEventMatcher`, and manifest structure to `ExtensionManifest`/`LoadedExtension`, keeping its own responsibility limited to running one extension's JavaScript; `ExtensionHostInstaller` in turn delegates code identity to `InstalledIdentity`/`FileSignature`, per-namespace adaptor behavior to the eight `MainThread*` types, and unimplemented-member bookkeeping to the standalone `NotImplementedLedger`, none of which any of these three files re-implements. `unit-test-coverage` passes: `ExtensionHostTests.swift` (75 `@Test` functions), `ExtensionHostInstallerTests.swift` (6), `ExtensionHostTimerClampTests.swift` (9), and `NotImplementedLedgerTests.swift` (14) together exercise entry-point resolution and refusal, the full activation-state precedence and terminal-boundary contract, cancellation-versus-failure semantics, the complete timer lifecycle including every clamp boundary, `defineVSCodeMember` across every host state, hostile-JavaScript defenses, the ledger's dedup/probe/sort contract, and the installer's identity-based reconciliation and workspace-scan race guard — as traced in the Conformance Test Vectors above. `fault-tolerance` passes because a compile or module-load failure that runs no extension code leaves the host retryable rather than spent (failure-before-boundary-is-retryable), a thrown subscription disposable never strands the rest of the teardown list (dispose-subscriptions-idempotent), and an adaptor's misspelled namespace withdraws itself rather than failing every future activation (define-vscode-member-withdraws-on-refusal). `idempotent-operations` passes because `activate()` shares one outcome across concurrent callers and is a no-op once activated (activate-idempotent-shared-outcome), `dispose()` and `disposeSubscriptions()` are both safe to call more than once (dispose-idempotent, dispose-subscriptions-idempotent), and `reconcile()` leaves an extension whose identity has not moved untouched. `explicit-error-handling` is `partial`: every activation-time failure is a typed, `Equatable` `ExtensionHostError` with its own `errorDescription`, but `ExtensionHostInstaller.scan(roots:)` silently swallows a `resourceValues(forKeys:)` failure via `try?` (treating an unreadable directory entry as simply "not a directory" and continuing) with no completeness signal analogous to `ExtensionRegistry`'s own `establishedIdentifiers`/`readEverything` pattern for the same class of failure — see the open question on workspace-scan-incomplete-signal above.
