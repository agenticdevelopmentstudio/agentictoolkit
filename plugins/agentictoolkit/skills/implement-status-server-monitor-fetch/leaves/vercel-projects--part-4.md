# Status Server Monitor Fetch Vercel Projects — continued (part 4)

## Platform Notes

- **SwiftUI**: not a SwiftUI concern (no view). An Apple companion backend embedding this polling pattern would model `VercelProjectsResult` as a `Sendable` `struct { ok: Bool; states: [VercelProdState]; meta: [VercelProjectMeta]; deploys: [ProviderDeploy] }`, the two module-scope caches (`teamSlugCache`, `domainListCache`) as `actor`-isolated state so a concurrent read/write from two `Task`s cannot race the way two same-thread JavaScript calls can, and the domain/backfill fan-outs as `TaskGroup`s capped to 8 concurrent child tasks (mirroring `mapLimit`'s "at most `limit` in flight" contract by hand, since structured concurrency has no direct equivalent). The distinct 5,000ms-fixed vs. deadline-derived timeouts are worth preserving explicitly, e.g. via two separate `Task.sleep`-racing helpers rather than one shared timeout wrapper.
- **Compose**: same non-UI framing as SwiftUI. A Kotlin port models the two caches behind a `Mutex`-guarded holder (or a `StateFlow` if a later reader needs to observe slug/domain changes), the bounded fan-outs with `kotlinx.coroutines`' `Semaphore(8)` guarding a `coroutineScope { names.map { async { ... } } }`, and the fixed-vs-shared-deadline timeout distinction with two separate `withTimeoutOrNull` call sites rather than one shared client-level timeout (Ktor/OkHttp's own timeout config is static per client, not computed per call the way this file recomputes `remaining` before nearly every request).
- **React/Web** (source platform): lives at `packages/web/packages/status-server/src/monitor/fetch-vercel-projects.ts` as a set of plain async/pure functions on the Node status backend, imported by `sync.ts`'s poll cycle and by `deploy-projects`/`integrations` reconciliation routes (both external); it depends on four sibling in-repo modules (`./time-ago`, `./deploy-status`, `./format`, `./provider-deploy`) and two exports of the vendored `@agentic-toolkit/deploy-platform` package (`util`'s `mapLimit`, `cooldown`'s `noteRateLimited`/`rateLimitedUntil`) — none of it is client-side React.
- **AppKit / UIKit**: same non-UI framing as SwiftUI. A macOS/iOS agent embedding this pattern has no Node-`Worker`-per-thread module-duplication concern to solve for its OWN caches the way this file's `teamSlugCache`/`domainListCache` implicitly have (per the Concurrent Access edge case above) — a Swift `actor` wrapping each cache is a single shared instance regardless of which thread or `Task` calls into it, so the "each thread gets its own copy" quirk this file exhibits has no direct analogue to reproduce; it would need to be deliberately introduced (e.g. one actor instance per isolation domain) to match this file's behavior, or more likely simply avoided as an improvement.
- **WinUI 3**: a .NET port models `ProviderDeploy`, `VercelProjectMeta`, and `VercelProdState` as `record`s with the same fields this file populates, the two 1-hour caches as `IMemoryCache` entries (or a hand-rolled `(value, expiresAt)` tuple behind a `lock`, matching this file's own hand-rolled TTL check rather than pulling in a full cache library), the bounded fan-outs as `Task.WhenAll` over a `SemaphoreSlim(8, 8)`-gated set of tasks (acquire before starting a project's `Task`, release in a `finally`, the direct `mapLimit` analogue), and each request via `HttpClient.GetAsync` with a `CancellationTokenSource` whose `CancelAfter` is computed per call from either the shared deadline (`remaining`) or a fixed 5,000ms literal — not `HttpClient.Timeout`, which is static per client and cannot express either "whatever time is left in the overall budget" or "skip the call below a minimum window" (slug-minimum-call-window) without per-call logic layered on top. Vercel's JSON bodies deserialize via `System.Text.Json` records shaped like `VercelDeploymentSummary`/`VercelProject`/`VercelDomain`; `toValidDate`'s accept-ISO-or-epoch-or-Date, reject-anything-else contract is worth porting explicitly over `DateTime.Parse`, which throws by default rather than returning a sentinel. The cross-thread cooldown registry this file gates on (`SharedArrayBuffer`/`Atomics` in `provider-cooldown.ts`, external) has no direct .NET analogue needed for a single-process Windows App SDK host; a `static` field guarded by `Interlocked`/`lock` suffices there, unlike this file's OWN two caches, which — per the Concurrent Access edge case — are NOT cross-thread shared in the source and so need no special treatment to match on a single-process .NET host either.

## Design Decisions

- **Decision**: resolve the team dashboard slug (`fetchTeamSlug`) only AFTER project enumeration, domain resolution, deploy derivation, and the blind-project backfill have all run, rather than at the top of the function.
  **Rationale**: stated directly in the source's doc comment on `fetchTeamSlug` — a 2026-07-26 production incident logged `Vercel team lookup /v2/teams/team_… failed: aborted due to timeout` because the slug lookup ran FIRST and off the same deadline, so "two 6s timeouts could take 12s of the 18s budget and truncate the page walk behind it," which made the caller skip the `deploy_project_meta` prune and skip narrowing the owned target set — "a project deleted at Vercel keeps its unclearable Problem." The slug is "decoration on top of the enumeration," per the same comment, so it "may only ever spend what the enumeration didn't need."
  **Approved**: pending
- **Decision**: memoize the team slug for 1 hour and, on a failed lookup, keep the previously cached slug rather than overwriting it with `null`.
  **Rationale**: stated directly in the source comment — "a team's slug changes ~never, so it is memoized module-scope for an hour," and the `remember` helper's own comment: "a failed lookup must not erase a good slug — see the `updateIssue` guard in issues.ts, which likewise refuses to overwrite a live link with this cycle's null." This is also what lets a budget-starved cycle keep every project's dashboard link instead of dropping them all to `null`.
  **Approved**: pending
- **Decision**: reconstruct `errored` against the newest CONCLUSIVE production deployment but reconstruct `behind`/`liveCreated` against the newest PROMOTED one, rather than using one reconstruction for both, whenever `targets.production` is itself a canceled skip.
  **Rationale**: stated directly in the doc comment on `evaluateProdStaleness` — the two questions need different anchors: "`errored` asks 'did the last real attempt on production fail?' → newest CONCLUSIVE," while "`behind` asks 'is a newer READY build sitting unpromoted?' → it must measure against what is actually SERVING... Measuring against the newest conclusive would compare that unpromoted build to itself and report healthy — killing the very signal this check exists for."
  **Approved**: pending
- **Decision**: always resupply BOTH a project's newest deployment and its newest conclusive one (when they differ) from `latestDeploysOf`, rather than the newest deployment alone.
  **Rationale**: stated directly in the doc comment on `latestDeploysOf` — supplying only the newest "lets the last REAL outcome age out of the team-wide recent-deployments window and vanish from the DB, leaving the recorders with nothing conclusive to judge: a fixed build can then never resolve its open issue, and a failed one can never open."
  **Approved**: pending
- **Decision**: additionally backfill a project's verdict from the `/v6/deployments` endpoint directly, but ONLY for a project whose entire polled window is skips, and only best-effort (a failed backfill never fails the poll).
  **Rationale**: stated directly in the doc comment on `fetchNewestConclusiveDeploy` — this is "the last line of defence": even the 10-deep window and the always-resupply contract above can't help "a site left untouched for 10 straight commits," so this endpoint, which "has no window to age out of," is consulted directly, but "called ONLY for projects whose window holds no verdict, so it is normally zero calls per cycle," and a failure here must leave "a blind spot" as "a blind spot" rather than compounding into a poll failure.
  **Approved**: pending
- **Decision**: raise the per-project `latestDeployments` request depth from Vercel's own default of 2 to 10 (`LATEST_DEPLOYMENTS_DEPTH`).
  **Rationale**: stated directly in the source comment — "EVERY commit to main creates a deployment on EVERY project," so at the default depth "a project's last real verdict falls out of the window after just TWO commits, and 36 of our 145 projects were already past it," while 10 (Vercel's API max) is "the cheap depth win: same call, no extra requests."
  **Approved**: pending
- **Decision**: retry a stalled or failed `/v9/projects` page fetch exactly once, immediately, on the same box, rather than with a backoff delay or additional attempts — and apply no retry at all to the team-slug, domain, or blind-backfill calls.
  **Rationale**: stated directly in the source comment on the retry loop — "the walk itself is not slow: ... 2 pages and ~1.5s wall for 163 projects," and what actually crosses the 6s per-call box is that "page 0 carries a 4MB body, and every poll starts on a COLD connection... The retry runs on the connection the first attempt just established, so it is the warm case." A second retry, a backoff delay, or extending the same treatment to the slug/domain/backfill calls is not described anywhere in the source as considered; those three call sites are recorded here per this recipe's authoring rules as a fact to state, not a gap to excuse — each relies on this file's own 1-hour caches (slug, domain) or the next poll cycle (backfill) to recover from a single failed attempt.
  **Approved**: pending
- **Decision**: let an exception outside the page loop's and the sub-calls' own `try`/`catch` blocks (e.g., an unexpectedly-shaped project) fall through to one OUTER `try`/`catch` that discards the entire call's progress, rather than wrapping the metadata mapping, deploy derivation, and staleness evaluation in their own per-project guards.
  **Rationale**: not stated as a deliberate tradeoff in an inline comment; recorded here as a fact of the code's structure per this recipe's authoring rules. Every genuinely EXPECTED failure mode (a bad HTTP status, a thrown fetch, an unparseable `createdAt`) already has its own local `try`/`catch` or validation step and degrades to a documented partial; the outer `try`/`catch` exists as a last-resort net for the unexpected, and its cost — discarding already-fetched pages on a truly unexpected exception — is the one asymmetry between that failure mode and every other truncation cause this file otherwise takes care to make partial-preserving.
  **Approved**: pending
