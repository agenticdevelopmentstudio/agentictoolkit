## Edge Cases

- **Null and empty input**: `env.VERCEL_API_TOKEN` absent, `undefined`, or an empty string all satisfy the same falsy check and MUST produce the `{ ok: true, states: [], meta: [], deploys: [] }` no-op (noop-missing-token) — MUST. `env.VERCEL_TEAM_ID` absent MUST cause every request to omit its `teamId` parameter, and the slug fallback MUST take the first entry of the token's team list rather than attempting to match an id (slug-direct-then-list-fallback) — MUST. A project with `latestDeployments` absent or `null` MUST be treated as `[]` by `latestDeploysOf` via `p.latestDeployments ?? []`, yielding zero deploy rows for that project (deploy-rows-require-real-target) — MUST.
- **Boundary values**: exactly `PROJECTS_CALL_ATTEMPTS` (2) attempts are made per page before a stall is treated as `"page-timeout"`; a third attempt is never made (per-page-retry) — MUST. Exactly 50 page iterations are permitted; a 51st page's project data is never fetched, and — because nothing sets `truncated` in that specific exit path — the resulting `ok` reflects only whichever of the three tracked causes fired earlier in the walk, or `true` if none did, even though the enumeration is genuinely incomplete (page-iteration-cap, ok-reflects-tracked-truncation-only) — MUST, stated as the code's actual, unguarded boundary behavior at this hard cap. A team-slug lookup with fewer than 500ms (`MIN_SLUG_CALL_MS`) remaining before the deadline is never issued at all (slug-minimum-call-window) — MUST. A `liveCreated` of exactly `0` is treated as unknown rather than as the Unix epoch (zero-created-at-treated-as-unknown) — MUST.
- **Concurrent access**: within one call, this function has no shared mutable state across its own local variables (`projects`, `states`, `meta`, `deploys`, `domainByName`) — each is freshly created per invocation. Two module-scope caches ARE shared across calls on the SAME thread: `teamSlugCache` (a single-entry object) and `domainListCache` (a `Map`, keyed by project name). Both are ordinary JavaScript module-level bindings, not the `SharedArrayBuffer`-backed registry `provider-cooldown.ts` (external) uses specifically to stay visible across the monitor's worker thread and the API's main thread — so, per that module's own documented reason for existing, a monitor-cycle call running on the worker thread and a `/deploy-projects`/`/integrations` call running on the API thread (external) each hold their OWN independent copy of `teamSlugCache` and `domainListCache`, and a cache warmed by one thread is invisible to the other. Two concurrent calls on the SAME thread can both observe a cache miss for the same key, both issue their own request, and both write the cache afterward; the `remember` and cache-set logic never corrupts the stored value (last write wins, and a failed lookup can only keep or restore a good slug, never null it out), but the two calls do duplicate the network round trip — MUST NOT be assumed to dedupe concurrent same-thread callers. The shared cooldown registry itself (`rateLimitedUntil`, `noteRateLimited`) IS visible across threads by construction of its `SharedArrayBuffer` — MUST.
- **Error states**: a non-ok per-page response, a thrown per-page fetch, a non-ok or thrown domain lookup, a non-ok or thrown slug lookup, and a non-ok or thrown blind-project backfill call are each caught at their own call site and degrade to a documented fallback (partial pagination, `[]`/cached domains, `null`/cached slug, `null` backfill row respectively) without throwing past that call — MUST. A 429 response is recorded to the shared cooldown registry via `noteRateLimited("vercel", ...)` ONLY when it occurs on the main `/v9/projects` page fetch; a 429 from the team-slug lookup, the domain lookup, or the blind-project backfill's `/v6/deployments` call is treated as an ordinary non-ok response by that call site (falling back to cache or `null`) and is NOT separately recorded to the cooldown registry — stated as fact, MUST. An exception thrown OUTSIDE any of those per-call `try`/`catch` blocks — e.g., from a malformed `p.link`, `p.targets`, or deployment shape reaching the metadata mapping, `latestDeploysOf`, or `evaluateProdStaleness` — is caught only by the function's OUTER `try`/`catch`, which logs it and returns the fully empty `{ ok: false, states: [], meta: [], deploys: [] }`, discarding every project, state, and deploy already assembled in that call (unexpected-exception-discards-partial-progress) — MUST.
- **Offline / disconnected state**: every network call this function makes — the page fetch, the team-slug lookup, the per-project domain lookup, and the blind-project backfill call — carries its own `AbortSignal.timeout` bounded by either the shared overall deadline (page fetch, slug lookup) or a fixed value (5,000ms for the domain lookup and the backfill call), so a fully offline or unresponsive Vercel API degrades to the same abort-then-fallback path documented under Error States for each call, rather than hanging the whole poll indefinitely — MUST. This file's own retry is limited to exactly one immediate retry of a stalled/failed PAGE fetch (per-page-retry); the team-slug lookup, the domain lookup, and the blind-project backfill call each make exactly one attempt with no retry of their own — SHOULD NOT be assumed to recover an offline slug/domain/backfill call within the same cycle; the next poll cycle (roughly 5 minutes later, per the caller's cadence, external) is the only retry for those three call sites.
